### Troubleshooting (Java)

- **Build fails on Railway:** the API builds from `szczur-radar-api/Dockerfile` (the build log starts with `load build definition from szczur-radar-api/Dockerfile`): stage `eclipse-temurin:25-jdk-noble` runs `./mvnw -B dependency:go-offline`, then `./mvnw -B -DskipTests package`; runtime `eclipse-temurin:25-jre-noble`. Check that `mvnw` is executable, `.mvn/wrapper/maven-wrapper.properties` is committed and `.dockerignore` does not exclude `mvnw`, `.mvn/`, `pom.xml` or `src/`; reproduce with `docker build -t szczur-radar-api ./szczur-radar-api` (CI `api-container-smoke` builds the same file). The Temurin tags move (`25-jdk-noble`, `25-jre-noble`): a failure on an unchanged commit points at a new base image. (Before `api-docker-image`: Railpack with `RAILPACK_JDK_VERSION=25`.)
- **Pre-deploy `migrate` fails:** read the pre-deploy logs. An `APPLICATION FAILED TO START` block with `Invalid LLM configuration: …` (and the line `migrate: invalid configuration: …`, exit code 2) → fix the named `LLM_*` variable(s): the three required ones set, durations by the rule in "Rule for variables"; JDBC errors → check the `PG*` references; Flyway validation error → never edit an applied migration, add a new one.
- **Healthcheck fails / proxy 502:** the API listens on `$PORT` (8000) dual-stack; a 502 only during the first seconds after sleep is the JVM starting (the proxy retries up to 30 s); a lasting 502 → API crashed, read its logs.
- **Two api deploys after one merge:** expected when the merge also changes the service's configuration. The GitHub autodeploy (after Wait for CI) builds the commit, and every environment patch triggers its own deploy of the same service: the CI job `railway-config` applying a real change from `.railway/railway.ts` (e.g. #33 cleared the start command — deploys 18 s apart), or a variable changed without `--skip-deploys` / committed in the dashboard (#31 + the `LLM_*` settings — 6 min apart). The earlier deploy ends `REMOVED`; only build minutes are lost. `railway config apply` has no option to skip the deploy, so the IaC case is accepted (avoiding it would mean replacing the GitHub autodeploy and its Wait-for-CI gate with a deploy from CI). Merges that change neither deploy once.
- **Every merge redeploys every service (until 2026-10-15):** `.railway/railway.ts` declared `watchPatterns` at the top level of each service, a field SDK 3.11 does not have; it was dropped without an error, so production had no watch paths (`build.watchPatterns: null` in the live config) and each commit on `main` redeployed the API, web and both crons, docs-only merges included. On 2026-10-13 the docs merge #55 restarted the API at 17:58 UTC and interrupted a running pipeline run (`PipelineStartupRecovery`: 2 runs `interrupted`, 4 posts put back). Fix (`fix/railway-watch-patterns`): `build: { watchPatterns: [...] }`; the production plan showed exactly four `safe` changes, `build.watchPatterns (null → ["<dir>/**"])`. Its merge redeploys the four services once (a config apply). Afterwards a commit that touches no service directory should deploy nothing (Railway marks it `SKIPPED`; check on the first docs-only merge), while one that touches `szczur-radar-api/` still restarts the API, so the no-merge rule for a `RUNNING` run stays. Check a new IaC field in the live config (`railway` MCP `get-service-config` or the dashboard), not only in the file.
- **Rule for variables:** always `railway variable set … --skip-deploys`, all variables of one change in one go, then one deploy: set them before the merge (the merge's deploy picks them up) or run one `railway redeploy` afterwards; in the dashboard, stage every change and press Deploy once. Durations always with a unit (`300s`, `5m`): Spring reads a bare number as **milliseconds** (`LLM_TIMEOUT=120` = 0.12 s). Since S-10 (`llm-config-fail-fast`) the code enforces this for `LLM_TIMEOUT`, `ACTIVATION_LINK_TTL` and `PIPELINE_STALL_TIMEOUT` (`settings/DurationSetting`): a whole number with a lower-case unit `ns`, `us`, `ms`, `s`, `m`, `h` or `d`, within the setting's range — `LLM_TIMEOUT` `10s`–`30m`, `ACTIVATION_LINK_TTL` `1m`–`7d`, `PIPELINE_STALL_TIMEOUT` `1ms`–`1d`; a bare number, ISO-8601 (`PT5M`), a fraction or a value out of range is refused with a message naming the variable and the value. A bad `LLM_*` value stops the pre-deploy `migrate` (an `APPLICATION FAILED TO START` block, exit code 2), so the deploy fails and the previous version keeps running; a bad `PIPELINE_STALL_TIMEOUT` stops the new server's start the same way; a bad `ACTIVATION_LINK_TTL` stops only `create-user` / `reset-password` (exit 2).

## api-docker-image: obraz Dockera dla API i wyłączenie PITR

### How the API is built and run

- Railway auto-detects `szczur-radar-api/Dockerfile` in the service root directory (like web). Build stage `eclipse-temurin:25-jdk-noble`: `./mvnw` with dependencies in their own layer, tests skipped (CI runs them). Runtime stage `eclipse-temurin:25-jre-noble`: user `app` (uid 999, non-root), `WORKDIR /app`, jar at `/app/target/szczur-radar-api.jar`, `ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "/app/target/szczur-radar-api.jar"]`, no `CMD`.
- `.railway/railway.ts` sets no start command (the `ENTRYPOINT` starts the server). The pre-deploy `java -jar target/szczur-radar-api.jar migrate` is unchanged: Railway runs it in a container of the same image, replacing the `ENTRYPOINT`, relative to `/app` (verified in the PR env and on production).
- Same image locally and in CI: `docker build -t szczur-radar-api ./szczur-radar-api`; `docker run <image>` = server, `docker run <image> migrate` = migrations. CI job `api-container-smoke` builds the Dockerfile, checks the non-root user, runs the exact pre-deploy command against Postgres 18, then `/api/health` and `/api/ready`.
- `railway ssh` lands in a **root** shell (Railway SSH ignores `USER`); the app process runs as `app`.

### How the backup works

- **Service `db-backup`** (`.railway/railway.ts`). It is built from `tools/db-backup/Dockerfile`: `postgres:18` plus `rclone` and `jq`. It runs as a Railway cron service: `0 2 * * *` (UTC), `restartPolicyType: NEVER`, the same 2 vCPU / 4 GB cap. A run is `tools/db-backup/backup.sh` (details in `tools/db-backup/README.md`):
  1. `pg_dump` in custom format, without the session rows (`public.spring_session*`);
  2. a full restore of that dump into a throwaway Postgres 18 cluster inside the container, with named checks (tables, empty sessions, Flyway version, row counts between the counts taken before and after the dump);
  3. only then the upload.
  - Production only: outside `production` (`RAILWAY_ENVIRONMENT_NAME`) a run logs "skipped" and exits 0, unless `BACKUP_IN_ANY_ENVIRONMENT=true` is set on the service (to try a change in a PR env). The whole run has a time limit (`BACKUP_TIMEOUT`, default 2 h) and `pg_dump` waits at most 5 min for a lock: a hung run fails instead of blocking every later run (Railway skips a cron run while the previous one is active). Retention counts only the exact names the tool writes.
  - A run ends with exit code 0 only if every step passed. Anything else fails the cron run (status `CRASHED`), and Railway e-mails every failed run, in PR envs too (verified 2026-10-11). Each scheduled run shows up as a new deployment of the service.
  - **Update (S-05, 2026-10-13):** two corrections from the S-05 PR-env test (2026-10-12, section S-05 below).
    - No e-mail came for a crashed cron run, and no in-app notification either. The signal now relies on a custom notification rule the operator added in Railway Account Settings (event "deployment crashed", scope: all environments): a failed run then arrives as an in-app and push notification ("… deployment crashed"). Without that rule a failed `db-backup` run is silent. The e-mails of 2026-10-11 stay recorded as they happened.
    - A scheduled run reuses the cron service's existing deployment; it does not create a new one. The deployment's status is that of its latest run.
  - **Update (S-15, 2026-10-18):** the checks know every table and refuse a suspiciously empty copy (section S-15 below; `tools/db-backup/README.md`).
    - The restore check requires the tables of `tools/db-backup/tables.sh` that exist at the dump's Flyway version (a V5 dump passes without `activation_tokens` and `notifications`) and fails on a table `tables.sh` does not classify (`tables: unknown`).
    - Before the dump, a run fails (`CRASHED`, "nothing dumped", the bucket untouched) when `posts` is empty, or when a counted table has fewer rows than the newest manifest in `daily/`. After a restore on purpose, the operator lets one run through with `BACKUP_ACCEPT_SHRINK=<newest manifest without its extension>` on `db-backup` and a redeploy (restore runbook, step 8); the failed run's log gives that value. The consent expires by itself after the first copy (its manifest becomes the newest) and never covers an empty `posts`.
    - A newest manifest that cannot be read, or whose `counts_after` is not numbers with a `posts` count, fails every run with its name: if it is broken, rename it outside the name pattern (e.g. `….manifest.json.broken`, bucket → Files) and the next run skips it. The retention deletes exact names only, so the `.broken` file stays (in the NAS mirror too): delete it by hand once its dump has left the retention. A run also fails when every manifest in `daily/` is dated after it (a wrong clock or hand-made names): that is not a first copy.
- **Bucket `db-backups`** (region `ams`), one per environment with its own keys: a PR env never sees production's dumps (and since the review it does not back up at all, see above). The S3 name is the display name plus a hash (variable `BUCKET`). Objects:
  - `daily/szczur-radar-<yyyymmddThhmmssZ>.dump`, each with a `.manifest.json` (time, sha256, size, server and `pg_dump` versions, Flyway version, row counts, restore check result);
  - `monthly/szczur-radar-<yyyy-mm>.dump` with its manifest: a server-side copy of the first successful dump of each UTC month;
  - retention: 14 daily and 12 monthly copies.
- **No manual trigger in Railway.** A cron service runs only on its schedule. To run it sooner, set a temporary schedule in the dashboard (`db-backup` → Settings → Cron Schedule, e.g. `*/5 * * * *`, minimum 5 minutes) and set it back to `0 2 * * *` afterwards:
  - in a PR env, the next push's apply restores it from IaC;
  - on production nothing restores it until the next merge.
- **What a restore loses:** everything written after the dump, up to about 24 h. The sessions are not in the dump, so everyone logs in again. Missing posts can be fetched again with a range run for the missing days, but assessing them again costs LLM calls.
- **Cost:** today a dump is a few MB. The upload counts as service egress ($0.05/GB) and the bucket costs $0.015 per GB-month, so 26 copies cost cents a month.
- **Deleting the bucket** stages a change. After deploy the bucket is restorable for 52 hours, then its objects are destroyed (`docs.railway.com/storage-buckets`). The copies on the NAS and in Google Drive (runbook after the merge) do not depend on it.

### Runbook — restore the database from a dump (human only)

Restoring a database is an operator action (`infrastructure.md`). The agent prepares the commands and verifies read-only.

0. No run is `RUNNING` in `/admin`; the API is unavailable during the restore.
1. Pick the dump: normally the newest `daily/…dump`. Download it with its manifest, from the bucket in the dashboard (`db-backups` → Files) or from the NAS.
2. Check it locally:
   ```bash
   docker build -t szczur-radar-db-backup tools/db-backup
   docker run --rm -v "$PWD/dumps:/dumps:ro" szczur-radar-db-backup restore-check.sh /dumps/<name>.dump /dumps/<name>.manifest.json
   ```
   It must end with `restore-check: OK`. Run every client below from this image as well: it always has PostgreSQL 18, and an older host `pg_dump` or `pg_restore` refuses a version 18 server or archive.
3. Open a tunnel in its own terminal and keep it open:
   ```bash
   railway connect postgres -e <env> --tunnel-only -P 15432
   ```
   It prints the user, password and database. In the commands below, `PGPASSWORD` comes from your shell (`read -rs PGPASSWORD; export PGPASSWORD`), never from the command line.
4. **Always** dump the current database first, so the restore can be undone:
   ```bash
   docker run --rm -e PGPASSWORD -v "$PWD/dumps:/dumps" szczur-radar-db-backup \
     pg_dump -h host.docker.internal -p 15432 -U <user> -d <database> -Fc -f /dumps/before-restore.dump
   ```
5. Restore in one transaction (all or nothing):
   ```bash
   docker run --rm -e PGPASSWORD -v "$PWD/dumps:/dumps:ro" szczur-radar-db-backup \
     pg_restore --clean --if-exists --no-owner --no-acl --single-transaction --exit-on-error \
     -h host.docker.internal -p 15432 -U <user> -d <database> /dumps/<name>.dump
   ```
   `--clean` drops only the objects that are in the dump. If the current schema is newer than the dump's Flyway version (a table from a later migration), empty the schema and restore in **one** transaction instead, so that a failed restore leaves the database as it was:
   ```bash
   docker run --rm -i -e PGPASSWORD -v "$PWD/dumps:/dumps:ro" szczur-radar-db-backup bash -c \
     'pg_restore --no-owner --no-acl -f - /dumps/<name>.dump | psql -1 -v ON_ERROR_STOP=1 -h host.docker.internal -p 15432 -U <user> -d <database> -c "DROP SCHEMA public CASCADE; CREATE SCHEMA public;" -f -'
   ```
6. Redeploy the API: `railway redeploy -s szczur-radar-api -e <env> -y`. The pre-deploy `migrate` applies the migrations newer than the dump (fix-forward), and the new container gets fresh connections.
7. Verify:
   - `/api/ready` returns 200;
   - admin login works (everyone logs in again);
   - `total` from `/api/posts` matches the state at the time of the dump.

   Record the result in the issue.

**Status (2026-10-15): live on production** after the human merge of PR #50 (`13e371a`, 2026-10-13); the first night's run passed (section "Production after the merge" below); issue #18 closed. S-05 adds the cron service `pipeline-trigger`, which starts the pipeline every night, and the label "Dane zaktualizowane: …" above the feed. Change: `context/archive/2026-10-12-daily-scheduled-run-freshness/`.

### How the daily run works

- **Schedule.** `pipeline-trigger` (`tools/pipeline-trigger/`, declared in `.railway/railway.ts`) runs at `30 0 * * *` (UTC). In Warsaw that is 01:30 (winter) or 02:30 (summer), always after midnight, so yesterday is a complete day. Railway may start a cron run a few minutes late.
- **Start.** `trigger.sh` calls the API over the private network, straight to its port (`http://<API_PRIVATE_DOMAIN>:8000/internal/…`), not through the web's Caddy, which forwards only `/api/*`. The request `POST /internal/pipeline-runs/daily` carries `Authorization: Bearer <PIPELINE_TRIGGER_TOKEN>` and no body.
  - The API creates the same runs as the admin's button (`PipelineRunService.startRange`): a RETRY run first when posts are left over, then a RANGE run for D-2…D-1 of the Warsaw calendar, from every configured source.
  - The requester (`requested_by`) is the system account `scheduler@system.invalid` (migration `V6`, `user/SystemAccount.SCHEDULER`). It has `login_enabled = false` and no password, so it can never log in.
  - D-2 is fetched a second time. That catches posts the Wykop pagination missed the night before (S-02 review, F9). Posts already stored cost no LLM call, only about 7 more Wykop requests a night.
- **Answers of `/internal/**`.** The token is the only credential there: the chain is stateless, reads no session and sets no cookie, and the token means nothing on `/api/**`.
  - `POST /internal/pipeline-runs/daily`: 202 `[{id, kind}]` in execution order; 409 `pipeline_busy` while a run is queued or running; 503 `source_not_configured`; 401 without the token, with a wrong one, and always when the API has no `PIPELINE_TRIGGER_TOKEN`.
  - `GET /internal/pipeline-runs/{id}`: 200 `{id, kind, status, finishedAt, fetched, newPosts, assessedOk, assessedFailed, processingErrors, dead}`, or 404 `not_found`. The counters are for the cron's last log line. **Update (S-06, 2026-10-16):** the answer also has `startedAt`, `lastActivityAt`, `interruptionCause`, `step` (the running step, or `null`) and `assessTotal` (the posts the `assess` step took in, or `null`); the cron's heartbeat and an interrupted run's cause come from them (section S-06). **Update (S-08, 2026-10-18):** the answer also has `skipped` (the fetched elements that could not become a post); the cron's line per run shows it right after `fetched` (section S-08).
- **Retries and limits** (`trigger.sh`, defaults; `tools/pipeline-trigger/README.md`):
  - no connection or 502/503/504 (the API waking takes about 10 s, or the cron container's private network is not ready yet): every 2 s, up to `TRIGGER_WAKE_TIMEOUT` (`3m`). A 503 `source_not_configured` is not retried. Only a start request that never connected is retried: no answer after the connection was made (e.g. `TRIGGER_REQUEST_TIMEOUT`, `60s`) means the API may have queued the run, so the cron exits 1 ("the run may have started; check /admin") instead of starting a second run whose result would hide the first one's (implementation review F1);
  - 409 `pipeline_busy` (e.g. an admin's run): every `TRIGGER_BUSY_INTERVAL` (`60s`), up to `TRIGGER_BUSY_TIMEOUT` (`60m`);
  - polling every `TRIGGER_POLL_INTERVAL` (`30s`), up to `TRIGGER_RUN_TIMEOUT` (`90m`) for all runs together;
  - the whole cron run: `TRIGGER_TIMEOUT` (`3h`). A hung run fails instead of blocking later nights (Railway skips a cron run while the previous one is active).
- **Exit code.** 0 when every run is `succeeded` or `partial`; 1 when one is `failed` or `interrupted`, on 401 or another 4xx, on 503 `source_not_configured` or a timeout; 2 on a configuration error. The token goes to `curl` as a config on stdin, never as an argument, and is never logged. **Update (S-08, 2026-10-18):** an empty run is `failed`: a RANGE run whose source gave no post to store ends `failed` in the API, so the cron exits 1 by the same rule. Skipped elements next to good posts do not change the status or the exit code (section S-08).
- **Failure signal.** A non-zero exit makes the cron's deployment `CRASHED`. Railway reports that **only through a notification rule**: in the PR-env test (2026-10-12) a crashed run sent no e-mail and no in-app notification. After the operator added a custom rule in Railway Account Settings (event "deployment crashed", scope: all environments), the next failed run arrived as an in-app and push notification "Pipeline-trigger deployment crashed". The same rule covers `db-backup` (section F-01). A `partial` run exits 0: its failed posts show in `/admin` and the next run retries them; an active signal for `partial` is S-06. **Update (S-06, 2026-10-16):** the signal is an in-app notification for every admin (the bell in the header), given by a `partial` run with a dead post or a technical error and by every `failed` or `interrupted` run; a `partial` run with only retryable `failed` posts gives none. The cron's exit codes are unchanged (section S-06).
- **Environment guard.** Railway creates the cron in every environment (a PR env is a copy of production). Outside `production` (`RAILWAY_ENVIRONMENT_NAME`) `trigger.sh` logs "skipped" and exits 0 without a request, unless `TRIGGER_IN_ANY_ENVIRONMENT=true` is set on the service.
- **Recovery before the port.** The cron's request is often the one that wakes the API. Start-up recovery of unfinished runs (`PipelineStartupRecovery`) now runs in `SmartInitializingSingleton.afterSingletonsInstantiated`, before the web server opens its port, so it cannot mark the cron's new run `interrupted`.
- **What Railway shows for a cron (seen 2026-10-12).** A scheduled run reuses the service's existing deployment; it does not create a new one. Railway shows what a cron writes to stderr at level `error`, and `trigger.sh` logs every line to stderr, so a normal run looks red in the log view. The exit code says whether it failed, not the colour.
- **The label.** `GET /api/freshness` (any logged-in role) → `{"lastUpdatedAt": "<ISO-8601 UTC>" | null}`: the `finished_at` of a RANGE run, scheduled or an admin's, that ended `succeeded` or `partial`: of those, the one whose range reaches furthest, and of them the latest. An admin's run over older days leaves the date (implementation review F4). The feed shows "Dane zaktualizowane: <date, time in Warsaw>", "Dane nie były jeszcze aktualizowane." before the first such run, and nothing when the read fails (the list still works).
- **Time and cost.** About 270 posts a night, 12–25 min with 4 threads; about $0.13 a night on tier `default` and $0.07 on `flex` (F-02 estimate). A night after a provider failure (RETRY without a limit, then RANGE) takes up to about 50 min, still before the 02:00 UTC backup. **Update (S-09, 2026-10-20):** a night *during* a provider outage no longer goes through every post with all its HTTP attempts: three calls in a row that fail after their retries stop the run `failed` (the breaker, section S-09), and its posts wait without an attempt used. With 5xx that takes minutes; with time-outs each call can last up to `TransportRetry.maxCallDuration` (34 min with `300s` and `flex`). Every call that ends finding the provider unavailable moves the run's `last_activity_at`, so the 39 min watchdog never stops such a run before the breaker, whatever `PIPELINE_LLM_CONCURRENCY` is (implementation review, 2026-10-23); with one thread and time-outs the breaker needs three calls one after another, about 1.5 h on production. The next night's RETRY takes those posts, so that night is the one that may take about 50 min. A dump taken while a run writes is still consistent (`pg_dump` reads one snapshot).

### How accounts are created and recovered

- `create-user --email <e-mail> [--role user|admin]` creates an account without a password (role `user` by default) and prints its link.
- `reset-password --email <e-mail>` works on any existing account, the admin's included. In one transaction it:
  - clears the password;
  - deletes every session of the account (signed out everywhere);
  - replaces its link, so an earlier link stops working.

  The role stays. Setting the password through the link deletes the account's sessions again: a login that was already past its password check when the reset committed saves its session after the reset, and that session ends at the activation at the latest. Closing that window completely is parked after the MVP (`roadmap.md`, Parked).
- A system account (`login_enabled = false`, today S-05's `scheduler@system.invalid`) never logs in, so it never gets a link: `create-user` and `reset-password` refuse it with exit 1 ("… is a system account …") and write nothing, and a link to one is invalid like an expired one. `ck_users_login_password` would refuse its password anyway.
- `create-admin` stays the first-admin bootstrap. When an admin exists, it refuses and points to `reset-password` (lost access) or `create-user --role admin` (another admin).
- Run them in the API container:
  1. Wake the API: `curl https://<web-domain>/api/health`. A sleeping service has no container, and `railway ssh` then lands on Railway's SSH gateway and runs nothing.
  2. `railway ssh -s szczur-radar-api -e <env>`. In a checkout without `railway link`, prefix it with `RAILWAY_PROJECT_ID=<project-id>`.
  3. In the container shell (`/app`): `java -jar target/szczur-radar-api.jar create-user --email jan@example.com`. Type the e-mail without `< >`: the shell reads `<` as a redirect.

  Steps 2 and 3 also work as one command, without an interactive shell: `railway ssh -s szczur-radar-api -e <env> -- java -jar /app/target/szczur-radar-api.jar create-user --email jan@example.com`. Run it in your own terminal, not through an AI agent's session (e.g. `!` in Claude Code): the output, link included, would land in the agent's transcript. A link that was shown there counts as shared: if it is not used yet, replace it with `reset-password`.

  Neither command asks for a password, so neither needs an interactive terminal (unlike `create-admin`). Both start the full Spring context (~6–8 s) with the container's `PG*` and `LLM_*` settings.
- Output on stdout: one line with the account, its role, "One-time activation link, valid until `<UTC time>`", then the link alone on the last line: `<WEB_PUBLIC_URL>/activate#<token>`.
- Exit codes:
  - 0: link issued;
  - 1: refused (e-mail taken, no such account, or a system account; nothing written) or failed;
  - 2: usage or configuration error; the message names the option or variable (e.g. `Activation links are not configured: WEB_PUBLIC_URL …`).
- The person opens the link and sees "Ustaw hasło dla `<e-mail>`". After setting a password (12–128 characters), they land on `/login` with "Hasło ustawione. Zaloguj się." and the e-mail filled in. The page creates no session: they log in as usual.
- A used, expired or replaced link shows "Link jest nieważny lub wygasł. Poproś administratora o nowy." The fix is a new link: `reset-password` for that e-mail.

**The link is a secret.** Whoever holds it sets the account's password.
- The operator passes it to the person outside the system. Never paste it into an issue, a PR, this document or a log; record only that a link was issued.
- The token is in the URL fragment (`#`), so it never reaches Caddy's access log or the API's; the database keeps only its SHA-256. The command prints the link only on stdout, never on stderr or in the Spring log.

### Variables (`szczur-radar-api`, names only)

| Variable | Production | PR env |
| --- | --- | --- |
| `WEB_PUBLIC_URL` | from `.railway/railway.ts`: the template reference `https://${{szczur-radar-web.RAILWAY_PUBLIC_DOMAIN}}`, which resolves to `https://szczur-radar-web-production.up.railway.app` | the same declaration, resolved to the PR env's own web domain, `https://szczur-radar-web-szczur-radar-pr-<N>.up.railway.app` |

- Fallback, if a plan rejects or rewrites the template string: `WEB_PUBLIC_URL: preserve()` in `.railway/railway.ts`, and the operator sets the value in every environment (`railway variable set WEB_PUBLIC_URL=https://<web-domain> -s szczur-radar-api -e <env> --skip-deploys`). ## S-06: historia przebiegów i powiadomienia (pipeline-run-history-dashboard)

**Status (2026-10-18): live on production** after the human merge of PR #60 (`5b6eabb`); production verified, including the first night (section "Production after the merge" below); issue #19 closed. S-06 shows the admin what a run is doing and tells them when one needs attention: the live progress of a running run, a watchdog that stops a run without progress, the cause of an interruption, in-app notifications for admins (a bell in the header) and a page per run (`/admin/runs/:id`). The cron logs a heartbeat. Change: `context/archive/2026-10-15-pipeline-run-history-dashboard/`, issue #19.

### What it adds

- **Progress.** A running run's counters (ok, failed, dead, technical errors, LLM retries, flex fallbacks) grow after every post, together with its `last_activity_at`; the start and end of every step move `last_activity_at` too. Before S-06 the counters were written only when the `assess` step ended. `/admin` and the run page read a queued or running run again every 10 s.
- **Watchdog** (`pipeline/RunWatchdog`, in the API process). A run of this instance without activity for `PIPELINE_STALL_TIMEOUT` (production: `39m`) ends `failed` with the error `no progress for 39m 00s: the run was stopped`.
  - Its open steps are closed `failed`, its posts go back without an attempt, and the next queued run starts (e.g. the RANGE run behind a RETRY). Before S-06 a hung run blocked every later start (the run of 2026-10-09 "lasted" about 22 h).
  - It checks every minute. While the instance has no run it asks the database nothing, so the API can still sleep.
  - A step without progress inside (`fetch`, `store`) moves the activity only at its start and end, so it is stopped too if it alone lasts longer than the timeout.
  - The stopped run's agent action goes on in Embabel's thread but changes nothing (conditional writes; `pipeline/CLAUDE.md`). The stop interrupts its LLM calls in flight (the log says `Run <id> assess: stopped, N post task(s) not finished were cancelled`), so they free their threads at once, or within one `LLM_TIMEOUT` attempt when blocked in a read, without another attempt.
  - Every database call has an end too: the driver fails a statement that waits more than 300 s for the database's answer (`socketTimeout`, `szczur-radar-api/src/main/resources/application.properties`). A hung call fails after 5 min with a JDBC error (`An I/O error occurred while sending to the backend`, caused by `SocketTimeoutException: Read timed out`) instead of holding its thread until a restart. Nothing legitimate in the app or in `migrate` waits that long; only a second `create-admin` started while the first one waits for its password fails after 5 min instead of waiting.
- **Interruption cause.** An `interrupted` run has `interruption_cause`, and its open steps become `interrupted`:
  - `deploy`: a new deployment took over. Every run stores the `RAILWAY_DEPLOYMENT_ID` of the instance that queued it, and the new instance's start-up recovery sees another id;
  - `restart`: the same deployment, or an unknown one;
  - `shutdown`: the instance was stopping.

  The SPA shows "przerwany — nowe wdrożenie" (a neutral tone: expected after a merge), "przerwany — restart aplikacji" or "przerwany — zatrzymanie aplikacji".
- **Notifications** (in the app only). A run that ends `failed`, `interrupted`, or `partial` with a dead post or a technical error gives every admin who can log in one notification. **Update (S-09, 2026-10-20):** a technical error now also includes a single provider outage the run went on after (the call failed after its retries; no attempt used), and three outages in a row end the run `failed` (section S-09).
  - A `partial` run whose only failures are `failed` posts with attempts left gives none: the next run retries them. A usual night (about 2% failed posts, no dead post) therefore gives none.
  - No push, e-mail or webhook. The cron's exit codes are unchanged, so Railway's "deployment crashed" rule still reports exactly what it reported before (a cron run exits 1 when a run ends `failed` or `interrupted`, never for `partial`).
- **The admin's views.**

The last line of an `interrupted` run ends with `(cause …)`. Exit codes unchanged (`tools/pipeline-trigger/README.md`).

### How it works

- **Switch.** Every job's `runs-on` in `.github/workflows/ci.yml` takes the runner label from repository variables, first non-empty wins: `CI_RUNNER_PR` (pull_request), `CI_RUNNER_MAIN` (push to `main`), `CI_RUNNER` (both), else `ubuntu-latest`. A change applies to the next run, a new commit or `gh run rerun <id>` (rerun reads the variables again). A branch must contain the switch (GitHub reads `runs-on` from the branch's `ci.yml`).
- **Pool.** `CI_RUNNER=szczur-ci` since 2026-10-18. Every runner has the label `szczur-ci` and its own VM with its own Docker daemon (the smoke tests use fixed host ports 8080/8000/5432 and container names `web`/`api`):
  - `github-runner-1`: VM `github-runner` (Ubuntu 24.04, 4 vCPU, 7 GB, 61 GB disk) in the home Proxmox, always on; installed with `tools/ci-runner/setup.sh`;
  - `ci-pc-1-1` … `ci-pc-4-1`: KVM VMs (4 vCPU, 8 GB, 60 GB each) on the developer's Ubuntu PC, autostart with the PC; managed with `tools/ci-runner/pc_runners.py` (`create` / `delete` / `status`) as the `ci-admin` user (groups `libvirt`, `kvm`, no sudo).
- **Who gets a job.** GitHub gives a job to any idle online runner with the label; there is no priority. PC on: a run takes about 2 min (bounded by the `backend` job). PC off or in Windows: its runners are `offline` and Proxmox takes every job, one after another, about 7 min a run — no variable change (verified 2026-10-19).

### Variables (names only)

- Repository variables: `CI_RUNNER` (set: `szczur-ci`), `CI_RUNNER_PR`, `CI_RUNNER_MAIN` (unset). Secrets unchanged; the runners receive the same CI secrets as GitHub's runners did (`LLM_API_KEY`, `RAILWAY_API_TOKEN`, `WYKOP_KEY`, `WYKOP_SECRET`).

### Runbook (operator)

1. **No runner online** (Proxmox VM down; jobs `queued`, PR checks pending, Railway deploy `WAITING`): start the VM or the runner service (`systemctl status 'actions.runner.*'` on it). GitHub cancels a queued job after 24 h and Railway skips the deploy after 2 h — after a fix, `gh run rerun <id>`.

**Status (2026-10-19): live on production** after the human merge of PR #81 (`2abc64c`); production verification: issue #73 (closed automatically at the merge, reopened 2026-10-21 for the runbook after the merge below). Change: `context/archive/2026-10-18-safe-deploy-gate/`. S-14 closes the gaps C4–C7 of the post-MVP audit:

- a tuning variable set by hand stopped every deploy on `main`, because the plan proposed `variable.delete` (C7).

The gate's logic moved from inline `jq` in `ci.yml` to the tested tool `tools/deploy-gate/`. Its `README.md` is the reference for every script, exit code and limit; this section is the operator's view.

### Order of the jobs

- **Tests first.** The six test jobs and the new `deploy-gate-test` run in parallel. `railway-config` has `needs:` on all seven, so a red test skips the apply. The failed workflow then makes Wait for CI skip the code deploy too. "Config before code" still holds: Wait for CI waits for the whole workflow, `railway-config` included.
- **`railway-config`** (CLI `@railway/cli@5.67.1`, `timeout-minutes: 115`), in this order:
  1. "Web address and deploy window": the environment's web origin (`web-url.sh`) and the guard's deadline;
  2. the deploy guard (`wait-safe.sh`), always, also when the plan will be empty, because it protects the code deploy too;
  3. "Plan and gate": `railway config plan --json --out plan.pin > plan.json`, then `gate.sh`. The job summary lists the changes and the services the apply redeploys;
  4. `plan.json` kept as the artifact `railway-plan-<environment>` (7 days, values redacted by the CLI), also when the gate refuses;
  5. only when the plan has changes: a snapshot of the redeployed services' latest deployments, then `railway config apply --plan plan.pin --yes`. It applies exactly the checked plan, and refuses it if the environment changed since. Never `--confirm-destructive`;
  6. only after an apply: the check after the apply (`verify-apply.sh check`).
- **After the workflow** Railway deploys the code (Wait for CI). Each deploy status triggers the workflow `deploy-verify` (below).
- The guard stands before the plan: a pinned plan must live seconds, not up to 90 min of waiting.

### The gate's rules

`railway config plan --json` in CLI 5.67.1 carries only four fields per change: `kind`, `severity`, `summary`, `details`. Railway rewrites the change list with a server-side preview, and the CLI's output passes through the runner's `Change` struct (`src/commands/config/runner.rs`), which drops `address`, `field`, `before`/`after` and `deployEffect`. The rules therefore read `details` and `summary` (plan amendment of 2026-10-18, variant A). In this order:

1. **Environment.** `ok == true`, and the plan's environment name and project ID are the target's; otherwise the whole plan is refused.
2. **Destruction.** Every change with `severity == "destructive"` is refused (`resource.delete`, `variable.delete` among them), and so is a change with no or an unknown `severity`.
3. **Allowed kinds** (fail closed): `resource.create`, `resource.update`, `variable.set`, `domain.create`. Any other `kind` is refused whatever its `severity`.
4. **Source.** A `resource.update` that touches the source (a detail starting with `source.`, or `source` in `summary`) passes only when every detail is exactly `source.checkSuites (null → true)` or `(false → true)`: turning Wait for CI on. `source.branch`, `checkSuites true → null`, or `checkSuites` together with another source field are refused.
5. **Unknown format.** A change without `kind`, or a `resource.update` without `details` as a list of strings, is refused. The CLI gives no details for a rename or `networking`, so those are refused too.
6. **Restarts.** Every change counts as a redeploy of its resource (the CLI gives no `deployEffect`). The gate announces these and does not refuse them, Postgres included. The resource is found in the plan's `desiredGraph` from the change's `summary`; a restart whose resource cannot be found is refused. `restarts.txt` holds the names of the redeployed resources of type `service` or `database` (e.g. `db-backup`, `postgres`). A bucket has no deployments, so it appears in the summary as "no deploy" and not in the file.

Exit codes: 0 allowed (also an empty plan), 1 refused (`::error::` lines with the refused changes), 2 a bad call or an unreadable plan.

### The deploy guard

A deploy interrupts a pipeline run that is queued or running. The guard asks `GET <web>/api/deploy-safety` and holds the plan, the apply and, through the workflow's conclusion, the code deploy.

- **The endpoint** (`pipeline/api/DeploySafetyController`) is public and listed in `PUBLIC_ROUTES` ("CI deploy gate"). It reveals only whether a run is queued or running:
  - 200 `{"safe":true,"reason":null}`;
  - 200 `{"safe":false,"reason":"pipeline_running"}`, which wins over `"pipeline_queued"` when both are true;
  - 503 `{"status":"unavailable"}` without the database, like `/api/ready`.
- **Busy.** The guard logs the reason and asks again every `DEPLOY_GUARD_INTERVAL` (`60s`), up to `DEPLOY_GUARD_TIMEOUT` (`90m`) or the deadline (below), whichever comes first. Then it fails red with an `::error::` that points to this runbook.
- **The deadline.** Railway's Wait for CI gives up 2 h after the push. The guard therefore also has an absolute deadline: the workflow run's `created_at` (the same for every attempt of the run) + 120 min − `DEPLOY_VERIFY_TIMEOUT` (`15m`) − `DEPLOY_GUARD_WAKE_TIMEOUT` (`3m`, the /api/ready wait after the apply) − 5 min, i.e. 97 min after the run was created. A deadline already past at the start fails at once, without a request.
- **No decision means pass, with a warning:**
  - 401 or 404: the API has no such route (an older version). An API from before S-14 answers **401**, not 404: deny-by-default refuses a route outside `PUBLIC_ROUTES` without a session. The first merge of S-14 to production passes this way.
  - No connection or a 5xx: retried every 2 s up to `DEPLOY_GUARD_WAKE_TIMEOUT` (`3m`), which wakes a sleeping API. After that the guard passes with "API unavailable": no run can be in progress, and the deploy may be the fix.
  - Railway's edge answers 404 "Application not found" for a web service that is not deployed. The guard cannot tell that from an older API and passes with the "older API" warning (seen in the PR env, below).
- **Fails red:** a 200 without a readable verdict (e.g. HTML, or `safe:false` without a reason), any other status (3xx, 403), and a bad setting (exit 2).
- **Off switch:** the **repository variable** `DEPLOY_GUARD=off` (GitHub → Settings → Secrets and variables → Actions → Variables, or `gh variable set DEPLOY_GUARD --body off`). The guard then skips with a warning on every later run, PR envs included. Delete the variable as soon as the reason is gone (`gh variable delete DEPLOY_GUARD`). It is the emergency switch without a revert.
- **What it does not cover**, so the human rules stay: a run started between `safe:true` and the start of the deploy is still interrupted (S-06 notifies the admins), and the guard knows nothing of the night's schedule. Keep "no merge while `/admin` shows a run `RUNNING`" and "no merge between about 00:30 and 01:30 UTC" (section S-05).
- **Cost.** The guard adds about 1 min of Actions time per push. Waiting costs minutes only when a push meets a run, and its polling keeps the API awake meanwhile.

### Runbook — the guard waits or fails (operator)

1. **It waits.** The `railway-config` log shows `pipeline_running` or `pipeline_queued` once a minute. Usually nothing is wrong: an admin's run or the night's run (about 00:30–01:30 UTC) is in progress. Watch it in `/admin`. The guard passes on its first poll after the run ends, and the code deploys after the workflow.
2. **A zombie run.** A run stays `running` or `queued` in the database while nothing executes it (audit A2; the fix is S-11). The S-06 watchdog stops a run without progress only on the instance that runs it. Restart the API (`railway redeploy -s szczur-radar-api -e <env> -y`): its start-up recovery marks unfinished runs `interrupted` and puts their posts back. Then check that `curl -s <web>/api/deploy-safety` says `{"safe":true,"reason":null}`.
   - If the guard is still waiting, it passes on its next poll.
   - If it has already failed: **"Re-run failed jobs" works only before the deadline**, because the deadline counts from the run's creation, not from the re-run, and a re-run past it fails at once. Past the deadline, use a new push (on `main`: a new merge, by a human), or `railway redeploy --from-source -s <service> -e <env>` for the services whose code must deploy. A redeploy does not apply the commit's `.railway/railway.ts`, so when the commit changes it, only a new push applies it. Not verified yet: whether Wait for CI also holds back a `railway redeploy` of a commit whose workflow ended red (`deploy-verify` assumes it does). If the redeploy ends `SKIPPED`, push again.
3. **The guard itself is wrong** (e.g. the endpoint answers `safe:false` with no run in `/admin`, and a restart does not help): set `DEPLOY_GUARD=off`, re-run before the deadline or push again, fix the cause, then delete the variable.

**A guard that fails past the deadline.** The workflow at that commit ends red, so the code of that commit is not deployed. Railway marks its GitHub Deployment `inactive`, which triggers no workflow: `deploy-verify` stays silent and no alarm comes. The red `railway-config` job (GitHub's notice of a failed workflow) is the only signal. Recover as in step 2.

### The check after the apply

The incident of 2026-10-12 (a "safe" apply restarted Postgres, which hung for 9 min before anyone looked; section F-01) is now caught in minutes:

- Before the apply, `verify-apply.sh snapshot` stores the latest deployment ID of every service in `restarts.txt`. After it, `verify-apply.sh check` waits for a new deployment of each one (`railway deployment list --json --limit 1`, by project and environment ID, never `railway link`):
  - `SUCCESS` or `SLEEPING`: deployed;
  - `WAITING` or `QUEUED`: "handed over to deploy-verify". Wait for CI holds a deploy of a service with `checkSuites` until this workflow ends, so waiting here would deadlock;
  - `BUILDING`, `DEPLOYING`, `INITIALIZING`: wait; `REMOVED`, `REMOVING`: replaced by a newer one, so ask again;
  - `FAILED`, `CRASHED`, `SKIPPED`, `NEEDS_APPROVAL` or an unknown status: the job fails;
  - the same ID until the limit: the job fails ("the apply did not trigger a deploy of <service>").
- The limit for all services together is `DEPLOY_VERIFY_TIMEOUT` (`15m`). Then `GET <web>/api/ready` must answer 200 within `DEPLOY_GUARD_WAKE_TIMEOUT` (`3m`), otherwise the job fails.
- An empty `restarts.txt` checks only `/api/ready`.
- After a failed apply (the job is red anyway) the step "API after a failed apply" still asks `/api/ready`: a failed apply may already have restarted services, Postgres included, and the log then says whether the API still reaches its database.
- The sum of the limits (guard 90 min + check 15 min + `/api/ready` 3 min + plan and apply) must stay inside the 2 h window: never raise one without lowering another.

### `deploy-verify` and the `deploy-health` issue

No step of `ci.yml` can see the code deploy, which starts only after the workflow ends. Railway reports each environment's deploy as a GitHub Deployment `szczur-radar / <environment>`, and every status of it triggers `.github/workflows/deploy-verify.yml` (`on: deployment_status`).

- The job runs only for the states `success`, `failure` and `error` of a `szczur-radar / …` environment. Other events give a `skipped` job, which never blocks Wait for CI and costs no minutes.
- `tools/deploy-gate/verify-deploy.sh` (checkout at the deployed SHA): after `success` it probes `<web>/api/ready` and `<web>/healthz`, retried for up to 3 min while the services wake. Both 200 means a green run and no issue.
- After `failure` or `error`, or a probe without 200, it raises an alarm. It creates the label `deploy-health` if missing, then comments on the oldest open `deploy-health` issue with the environment's name in its title, or opens "Niezdrowe wdrożenie: <environment>". The text has the commit, the deploy state, the web address, a link to the run and each probe's result.
- Railway sends several statuses per environment and commit, without the service's name, so one deploy gives several runs. They go to one open issue, except that runs within about 2 s of each other may open two: GitHub's issue lists show a new issue only about 2 s after it is created (the REST list the script reads; `gh issue list --label` goes through the search index and lags further). Measured in the manual test of 2026-10-19 (#84–#87). Close a duplicate by hand.
- **The run ends green even after an alarm.** Wait for CI looks at the conclusion of every workflow at a commit. A red `deploy-verify` would make Railway skip a redeploy of the same commit, which may be the fix. Only a failing `gh` (the alarm did not get through) fails the run.
- **A `deploy-health` issue:** read the probes in it and the service's deploy logs, fix the cause, then close the issue by hand; nothing closes it automatically. The next unhealthy deploy of that environment opens a new one.

### The `concurrency` queue

`railway-config` has one group per environment (`railway-config-production`, `railway-config-pr-<N>`) with `cancel-in-progress: false`: a running apply is never cancelled. A waiting guard holds the group, and GitHub keeps only one pending run per group. A third push meanwhile cancels the pending second run. The second commit does not deploy on its own, but the third contains it.

### Ignored variables

`.railway/railway.ts` has the project policy `variables: { ignore: [...] }` (Railway CLI ≥ 5.64.0). The CLI removes an ignored key from both sides before the diff, so IaC never sets it and never deletes it. A hand-set value therefore no longer gives `variable.delete`, which the gate refuses.

| Pattern | Variables (`tools/db-backup/README.md`, `tools/pipeline-trigger/README.md`) |
| --- | --- |
| `db-backup/BACKUP_IN_ANY_ENVIRONMENT`, `db-backup/BACKUP_TIMEOUT`, `db-backup/S3_FORCE_PATH_STYLE` | the backup's tuning |
| `pipeline-trigger/TRIGGER_*` | `TRIGGER_IN_ANY_ENVIRONMENT` and every `TRIGGER_*` duration, `TRIGGER_HEARTBEAT_INTERVAL` included |
| `szczur-radar-api/JAVA_TOOL_OPTIONS` | extra JVM flags |

- A new hand-set tuning variable needs its pattern here, or a declaration in the file. Never ignore a key the file declares: declared and ignored is a plan error, and an ignored literal (e.g. `BACKUP_KEEP_*`) would vanish from both sides of the diff.
- `TRIGGER_IN_ANY_ENVIRONMENT: preserve()` is gone (the pattern covers it). The API's `preserve()` declarations stay.
- `railway config plan --json` shows the policy as `variablePolicy`. A field unknown to the SDK may vanish silently (`lessons.md`), so check it there.

### What changes

- **Empty run → `failed`.** A RANGE run (the cron's or an admin's) in which a source gave no post to store fails in the `fetch` step. "No post" means no element in the range, or only elements that could not become a post (unexpected JSON shape or not mappable).
  - `SourceIngest.fetch` fetches every source first, then throws `NoPostsFetchedException`. Step `fetch` is `failed` with the message; there is no `store`, `select` or `assess` step.

  - The run's `fetched` and `skipped` hold the real counts (written before the run fails), so a run with only skipped elements shows e.g. "pobrane 12, pominięte 12", not zeros.
  - The signals are those of any `failed` run: every admin gets an in-app notification (the bell with the badge "błąd"; the run's page gives the error text as the reason); the cron exits 1, so its deployment is `CRASHED` and Railway's "deployment crashed" rule sends a push; `GET /api/freshness` keeps the previous good run's date.
  - An admin's run over a range without posts (e.g. today, just after midnight) fails the same way and notifies the admins. That is the rule working, not an outage.
- **Skipped elements next to good posts → warning.** A run with `skipped` > 0 and at least one post ends as before (`succeeded` or `partial`), but it needs attention (`PipelineRun.needsAttention`).

  - The API logs one WARN per source with skipped elements: `Run <id>: <source> skipped <skipped> of <fetched> elements (unexpected shape or not mappable)`.
- **`skipped` everywhere.** `GET /internal/pipeline-runs/{id}` answers `skipped`; the cron's line per run and the API's end line show it right after `fetched`.
- **Unchanged.** RETRY and POSTS runs (no fetch step; a RETRY run with no post left still ends `succeeded`), runs without skipped elements, the cron's exit-code rule (1 only for `failed` / `interrupted`), the freshness query. No migration: `skipped` exists since `V3`.

## S-09: awaria dostawcy nie zabija postów (attempt-accounting)

**Status (2026-10-20): in progress** on branch `feature/attempt-accounting`, issue #68; not merged. Before S-09 an attempt was any stored `failed` result, so a provider outage (e.g. 20 min of 5xx from OpenRouter) used up an attempt of every post it hit, and three bad nights made posts `dead`. S-09 tells three faults apart. Change: `context/changes/attempt-accounting/`.

### What changes

- **The post's fault uses an attempt** (as before): the provider refused the request (a non-retryable 4xx, a refused or blocked answer, no text) or the model's answer broke the contract (`schema_violation`, `fabricated_evidence`, …). A stored `failed` result; the third makes the post `dead`.
- **The provider's fault uses none.** A call whose retries ran out on 429, 5xx, time-outs or connection errors (`TransportRetry`; with flex both tiers) means the provider is unavailable:
  - **three such calls in a row** (in the order they end, with no call answered by the model between them; a post the prefilter decides makes no call and does not end the streak) stop the run (the breaker, a constant in code). It ends `failed` with the error `stopped, the remaining posts were put back: the LLM provider is unavailable: 3 calls in a row failed after their retries; the last: failed after N attempts: <provider message>`. Every post goes back as it was: no attempt, no technical failure;
  - **progress, not a stall:** each such call that ends moves the run's `last_activity_at` without counting anything, so the watchdog (`PIPELINE_STALL_TIMEOUT`) stops only a call that hangs, and a run of time-outs ends with the breaker's error above at any `PIPELINE_LLM_CONCURRENCY`, never with `no progress for …`;
  - **a single outage** the run went on after is a technical error of its post: the post goes back without an attempt, counting one technical failure with its message, and the run counts a processing error, so it ends `partial`.
- **Our code's fault uses none, but has a limit.** An exception while assessing a post (a mapper, an unknown SDK exception in the LLM client — since S-09 no longer a `failed provider_error` — or a failed write) puts the post back without an attempt and counts one technical failure, as before in the run's `processing_errors`.
- **On hold.** A post with three technical failures in a row (`posts.technical_failures`, migration `V10`; single outages and errors of our code alike) is on hold: the RETRY run no longer takes it, and it alone queues no RETRY. It keeps its stage (`stored` or `failed`) and is on the list "Nieudane posty" in `/admin` as "wstrzymany · błędy techniczne N · <last error>", with its checkbox active. An admin's run of chosen posts ("Ponów zaznaczone") takes it. Every stored result (ok or `failed`) resets the count and the last error.
- **Flex.** A flex tier whose three attempts all failed, with any mix of 429, 5xx, time-outs and connection errors, moves the same call to the default tier (`flex_fallback = true`); before, only three 429s did. The longest call (`TransportRetry.maxCallDuration`) and so the watchdog's 39 min are unchanged.
- **Signals.** The breaker's `failed` run gives the signals of any `failed` run: an in-app notification for every admin, the cron's exit 1 (`CRASHED`) and Railway's "deployment crashed" push. A `partial` run with a single outage notifies like any technical error (section S-06). No new variable, no new counter of the run, no change to the answer's shape of `/api/admin/llm/check` (an unknown error there is now `"ok":false` with its message, cleaned of the key and logged, instead of a 500).
- **Migration `V10__posts_technical_failures.sql`.** Adds `posts.technical_failures` (default `0`, `CHECK >= 0`) and `posts.last_technical_error`. It only adds columns with defaults, so the old instance keeps writing during the deploy window. No new table, so `tools/db-backup/tables.sh` is unchanged. Fix-forward as always.
- **History unchanged.** Posts whose attempts outages used up before S-09 keep them, and `dead` posts stay `dead` (no data migration; reviving `dead` is out of scope). The query below counts them; `failed` ones an admin retries with the button.

### What the operator sees

**A provider outage** (the breaker):

- The run's page and `/admin`: status `failed` with the error above; the counters show no `failed` post and no technical error for the outage (`assessed failed 0`, `processing errors 0` unless other posts had them). The bell has a notification.
- API log: `WARN The LLM provider is unavailable in run <id>: 3 calls in a row failed after their retries; no further post is taken: failed after …`. The progress line counts the posts whose call found the provider unavailable: `Run <id> assess: 3/251 (ok 0, failed 0, dead 0, errors 0, unavailable 3), in flight …, retries …, flex fallbacks …`.
- The cron's line: `range …: failed (…, assessed failed 0, processing errors 0, dead 0)`, `FAILED: a run did not succeed: …`, exit 1, Railway's push.

**A single outage:** `WARN Assessing post <id> in run <id> found the LLM provider unavailable; the post was put back without an attempt, counting a technical failure: LlmUnavailableException: failed after …`; the run ends `partial`, its error lists the post (`1 post(s) with a technical error, no assessment stored: <post id> (LlmUnavailableException: …)`), and the admins get a notification.

**An error of our code:** `ERROR Assessing post <id> in run <id> failed; the post is put back without an attempt, technical failure N` with the stack trace; the run ends `partial`, its error lists the post.

### Runbook — provider outage (operator)

1. **Open the run's page** from the bell: the error says "the LLM provider is unavailable" and ends with the provider's last message (HTTP status or time-out).
2. **Nothing to repair in the data.** Its posts used no attempt and count no technical failure. Once the provider is back (its status page, or `GET /api/admin/llm/check` → `"ok":true`), either wait for the next night (the cron's RETRY takes the leftovers before the range) or start a range run from `/admin` (it queues a RETRY of the leftovers first). ### Runbook — a post on hold (operator)

1. **Find it** in `/admin` → "Nieudane posty": "wstrzymany · błędy techniczne N · <last error>" (the full error in the tooltip). The last error says whose fault the latest failure was: `LlmUnavailableException: …` = a provider outage the run went on after, anything else (e.g. `IllegalStateException: …` from a mapper or a client) = our code. The three may be mixed and come from different runs; only a stored result breaks the row.
2. **Fix the cause first.** For an error of our code that means a fix merged and deployed; for outages, the provider being back. A retry before that only adds another technical failure.
3. **Retry it:** tick it and press "Ponów zaznaczone" (a POSTS run). A stored result, ok or `failed`, resets its count and puts it back into the automatic RETRY.
4. Read-only, the posts on hold: `SELECT id, stage, technical_failures, last_technical_error FROM posts WHERE technical_failures >= 3 AND stage IN ('stored', 'failed');`.

### Query — posts whose attempts outages used up before S-09 (read-only)

`failed` and `dead` posts whose every stored `failed` attempt was an outage: class `timeout` or `provider_error` with the call's violation "failed after N attempts: …" (`TransportRetry`'s message for retries used up; the violations are a JSON array of `{failureClass, rule, path, message}`, with `rule` `call` for a call without an answer). Posts with a refusal or a contract violation among their attempts are not counted, nor the 15 posts of 2026-10-09 whose `provider_error` was "`choices` is not set" (section S-02 above). Run it in a read-only transaction (`railway connect postgres -e production`):

```sql
BEGIN READ ONLY;
SELECT p.stage, count(*) AS posts
FROM posts p
WHERE p.stage IN ('failed', 'dead')
  AND NOT EXISTS (
    SELECT 1 FROM assessments a
    WHERE a.post_id = p.id
      AND a.status = 'failed'
      AND NOT (a.failure_class IN ('provider_error', 'timeout')
               AND EXISTS (SELECT 1 FROM jsonb_array_elements(a.violations) v
                           WHERE v ->> 'rule' = 'call' AND v ->> 'message' LIKE 'failed after %')))
GROUP BY p.stage
ORDER BY p.stage;
ROLLBACK;
```

For the posts themselves, select `p.id, p.stage, p.assessment_attempts, p.published_at` instead of the count (and drop `GROUP BY`). A `failed` one can be retried from "Nieudane posty"; a `dead` one stays `dead`. Checked locally on 2026-10-21 on `postgres:18` after `migrate` (`V1`–`V10`) with test data (change `attempt-accounting`, `reviews/runbook-query-s09.md`): it counts a `dead` post with three outage attempts and a `failed` one with a time-out attempt, and leaves out a post with a `schema_violation` or a `fabricated_evidence` among its attempts, one with "`choices` is not set", one with a refusal (HTTP 400), an `assessed` and a `stored` one; both tables were unchanged afterwards.
